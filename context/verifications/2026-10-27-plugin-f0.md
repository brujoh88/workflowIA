# F0 del plugin `wf`: las cuatro dudas (D1–D4) — 2026-10-27

> Alcance: las dudas D1–D4 del plan `.claude/plan/2026-10-27-workflow-como-plugin.md` ·
> Entorno: local, Claude Code 2.1.311, Linux · Sesión: `session-20261027-1218-plugin-f0`

## Cómo se probó

- **Plugin mínimo** en la rama `feature/plugin-f0`, carpeta `spike/wf/`: un skill (`hola`), un hook
  `SessionStart` (`scripts/reglas.sh`) que inyecta `reglas/REGLAS.md` como `additionalContext`, y un
  `PreToolUse` sobre Bash (`scripts/guard.sh`) que deniega cualquier comando con `WF_BLOQUEAME`.
  La tienda (`.claude-plugin/marketplace.json`, nombre `workflowia`) está en la raíz del repo.
- **Testigo**: las reglas traen una contraseña de prueba que solo existe ahí. Antes de cada evento
  (resume, compact) se cambió, así que si Claude la sabe es porque el hook la volvió a inyectar y no
  porque la recuerda del historial. Además el texto inyectado lleva el evento que lo disparó:
  `[wf@0.1.0 inyectado en SessionStart:compact]`.
- **Rastro**: los dos lados (plugin y proyecto) escriben cada disparo en `.wf-spike.log`.
- **Repos descartables** (scratchpad, no versionados): `repo-prueba` (A), `repo-b` (B) y `repo-clon`
  (clon de B). Los dos primeros tienen hooks propios de proyecto (`SessionStart` y `PreToolUse`) que
  solo dejan rastro.
- **Dos vueltas**: primero con `claude --plugin-dir spike/wf`, después instalado desde GitHub
  (`brujoh88/workflowIA#feature/plugin-f0`, scope `project`). Tags publicados: `wf--v0.1.0`,
  `wf--v0.2.0` (con `claude plugin tag`).

## Resultados

### D1 · Las reglas llegan en los tres momentos — ✅ PASA

- **Esperado**: el texto de las reglas está en el contexto al arrancar, al hacer resume y después de compactar.
- **Observado** (igual con `--plugin-dir` y con el plugin instalado desde GitHub):
  - arranque: Claude responde `TUCUMAN-7731` y el log dice `SessionStart source=startup`.
  - resume: con la contraseña cambiada a `SALTA-4410` antes de reanudar, responde `SALTA-4410` y
    distingue la vieja como historial.
  - compact: después de `/compact`, el bloque `[wf@0.1.0 inyectado en SessionStart:compact]` está
    vivo en el contexto, aparte del resumen. El log registra `source=compact`.
- **Detalle a tener en cuenta en F2**: cada resume vuelve a inyectar las reglas enteras (no
  reemplaza la inyección anterior, se suma). Las reglas que viajen por acá tienen que ser cortas:
  se pagan una vez por cada arranque, resume o compact.

Plan B (copiar `REGLAS.md` al proyecto e importarlo con `@`) **no hace falta**.

### D2 · Los hooks del plugin corren junto a los del proyecto — ✅ PASA

- **Esperado**: en un mismo evento corren los dos, ninguno pisa al otro.
- **Observado**: en cada `SessionStart` y en cada `PreToolUse` de Bash el log tiene una línea
  `PROYECTO` y una `wf`, en el mismo segundo. `echo WF_BLOQUEAME` lo frena el guard del plugin aunque
  el hook del proyecto también corrió y lo dejó pasar.
- **Detalle**: no hay orden garantizado entre los dos (en el log aparecen en orden distinto según la
  llamada). Ningún hook del proyecto puede depender de que el del plugin haya corrido antes.

Plan B (encadenar los hooks del proyecto desde el plugin) **no hace falta**.

### D3 · Un proyecto fijo en una versión mientras otro actualiza — ❌ FALLA como estaba planteada · ✅ plan B funciona, con un ajuste

**Lo que falla**: fijar la versión con el `ref` de la tienda en el `settings.json` del proyecto.

- La tienda se registra **una sola vez por máquina** (`~/.claude/plugins/known_marketplaces.json`),
  con un único `ref`. El `ref` del settings del proyecto solo cuenta la primera vez.
  - A con `ref: wf--v0.1.0` en su settings: `plugin marketplace update` desde A deja la tienda en la
    rama (`973c972`, 0.2.0). El `ref` de A se ignora.
  - Registrar el tag "con otro nombre" (otra clave en `extraKnownMarketplaces`) no crea una segunda
    tienda: el nombre sale del `marketplace.json`, y Claude **re-apunta la única tienda `workflowia`
    de toda la máquina** al tag (lo avisa: *"was already added from … and now points at …"*). Eso
    arrastra a todos los proyectos que la usan.
- **Trampa encontrada**: `claude plugin update wf@workflowia -s project` corrido desde B, que todavía
  no lo tenía instalado, **actualizó la instalación de A** (la salida nombra la ruta de A) de 0.1.0 a
  0.2.0.

**Lo que sí funciona (plan B, "dos entradas de la tienda")**: una segunda entrada en el mismo
`marketplace.json`, con otro nombre y fijada al tag:

```json
{ "name": "wf-estable",
  "source": { "source": "git-subdir", "url": "https://github.com/brujoh88/workflowIA.git",
              "path": "spike/wf", "ref": "wf--v0.1.0" } }
```

- A instala `wf-estable@workflowia`, B instala `wf@workflowia`. En la misma máquina y al mismo
  tiempo, A arranca con `wf@0.1.0` (`JUJUY-2290`) y B con `wf@0.2.0` (`CORDOBA-0200`).
- El caché guarda cada una por separado (`cache/workflowia/wf-estable/0.1.0` y `cache/workflowia/wf/0.2.0`).
- **En los dos el skill se llama `/wf:hola`**: el prefijo sale del `name` del `plugin.json`, no del
  nombre de la entrada. Cambiar de canal no cambia los comandos.

**El ajuste respecto del plan**: lo que el plan llamaba `wf@estable` / `wf@siguiente` en la práctica
es `wf-estable@workflowia` / `wf@workflowia`. Y "fijar" no es por proyecto sino **por canal**: qué
versión es la estable se decide en el `marketplace.json` del workflowIA (moviendo el `ref` de la
entrada), y le llega a todos los proyectos que estén en ese canal. Un proyecto no puede pedir una
versión arbitraria por su cuenta. Para caluprobeauty alcanza: estable vs. siguiente.

### D4 · El recorrido de alguien que clona — ⚠️ PASA, pero el camino no se ve solo → plan B

Simulado: se borró la tienda del registro de la máquina, se clonó B (que declara la tienda y el
plugin en su `.claude/settings.json`) y se abrió Claude interactivo (tmux).

- **Primera apertura**: pregunta si se confía en la carpeta. Después la tienda **se registra sola,
  en segundo plano y sin avisar**, pero el plugin **no se instala ni carga**: el log del clon solo
  tiene la línea `PROYECTO`. No aparece ningún mensaje.
- **Reabrir**: igual. Sin aviso, sin plugin.
- **`/plugin`**: el plugin figura con error en la pestaña Errors: *"Plugin "wf" not cached … Run
  /plugin to refresh the plugin cache"*. "Enter to resolve" **no instala**: ofrece *desactivarlo
  para mí* o *desinstalarlo para todo el equipo*. Mal camino para un recién llegado.
- **Lo que anda**: una línea en la terminal, en la carpeta del clon, y reabrir Claude:
  ```
  claude plugin install wf@workflowia -s project
  ```
  `/wf:hola` responde `wf-hola OK`, el log tiene la línea `wf@0.2.0`, y `git status` queda limpio
  (no toca nada versionado).

**Plan B aplicado**: el README que genere `/setup` en cada proyecto lleva ese paso manual, arriba de
todo. **Mejora propuesta** (para F1, no se hizo): como los hooks del proyecto sí corren sin el plugin
(D2), `/setup` puede dejar un `SessionStart` mínimo del proyecto que, si no encuentra el plugin,
imprima la línea de instalación. Así quien clona se entera en la primera sesión aunque no lea el README.
